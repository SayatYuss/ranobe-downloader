## Создание релизной ветки (выполняется владельцем позднее)

После включения документации в `develop`:

```bash
git switch develop
git pull --ff-only
git switch -c release/0.3.0
```

В этой ветке затем обновить:
1. `pyproject.toml`: `version = "0.3.0"`; актуализировать описание и classifiers.
2. `CHANGELOG.md`: перенести заметки [Unreleased] в секцию `[0.3.0] — YYYY-MM-DD` с фактической датой.
3. README и документацию: проверить актуальность номеров версий, маршрутов, зависимостей.
4. Тесты, сборку и проверку итогового wheel.

Команды локальной финальной проверки:

```bash
python -m pip install -e '.[http,telegram,images]'
python -m unittest discover -s tests -v
python -m pip install build twine
python -m build
python -m twine check dist/*
cd web && npm ci && npm run build
```

`npm ci` требует зафиксированный `web/package-lock.json`. Если lockfile ещё не добавлен, сначала создай его через `npm install` и закоммить отдельно (или временно используй `npm install`).

## Публикация — отдельное решение владельца

После проверки и слияния релизных изменений в выбранную стабильную ветку:

```bash
git tag v0.3.0 <SHA_ПРОВЕРЕННОГО_КОММИТА>
git push origin v0.3.0
```

Отправка тега автоматически запускает workflow `.github/workflows/release.yml` и создаёт **GitHub Release**. PyPI этим workflow не используется. Проверить публикацию и собранные артефакты, затем объявить релиз.

**Внимание:** до обновления workflow он всегда выставлял `--prerelease`; для стабильной версии `0.3.0` это должно быть исправлено до отправки тега. Никогда не отправляй тег без осознанного решения опубликовать релиз.

## Известные ограничения

В настоящее время поддерживается RanobeLib; задача и прогресс HTTP API хранятся только в памяти; API не имеет собственной авторизации; Web UI пока использует заглушку вместо обложки; недоступные платные главы пропускаются. Они должны быть отражены в release notes.
