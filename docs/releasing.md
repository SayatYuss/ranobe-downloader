# Процесс выпуска

[Все руководства](README.md) · [Участие в разработке](../CONTRIBUTING.md)

Этот документ описывает выпуск новой версии проекта. Пользовательская установка описана в [руководстве Desktop](desktop.md).

## Подготовка

1. Рабочая ветка создаётся от актуального `develop`.
2. Версия обновляется в `pyproject.toml`, `CHANGELOG.md` и документации. Тег без префикса `v` должен совпадать с версией пакета.
3. Изменения проходят через PR в `develop` и проверки Python, Web UI и PySide6.
4. Сборки EXE, DMG и AppImage проверяются на целевых ОС. Минимальная ручная проверка охватывает скачивание, диапазон глав, очередь, отмену, историю, keyring и трей.
5. После проверки `develop` сливается в `main` отдельным PR. Прямой push в защищённые ветки не используется.

Сборки для ручной проверки находятся в GitHub Actions, в артефактах запуска **PySide6 desktop**. Архивы называются `pyside6-windows`, `pyside6-macos` и `pyside6-linux`. Коммит запуска должен совпадать с проверяемой версией.

Проверки из активного окружения:

```bash
python -m pip install -e '.[desktop,http,telegram,images]'
python -m unittest discover -s tests -v
python -m pip install build twine
python -m build
python -m twine check dist/*
```

На Linux без дисплея задайте `QT_QPA_PLATFORM=offscreen`. В `web` отдельно выполните `npm ci` и `npm run build`.

## Публикация

Тег создаётся на проверенном коммите `main` при чистом рабочем дереве. `X.Y.Z` обозначает новую версию пакета:

```bash
git switch main
git pull --ff-only
git status --short
git tag -a vX.Y.Z -m "Release vX.Y.Z"
git push origin vX.Y.Z
```

Отправка тега запускает workflow публикации. Опубликованный тег не перемещается и не используется повторно для другой сборки.

Workflow `Release` сверяет тег с версией пакета, запускает тесты и собирает дистрибутивы. Выпуск содержит wheel, исходный архив, архив Web UI, EXE, DMG и AppImage. После успешной сборки Python- и desktop-артефактов wheel и исходный архив публикуются в PyPI через Trusted Publishing. Остальные файлы остаются только в GitHub Release.

Предварительный выпуск определяется шаблоном workflow: `a`, `b`, `rc` или `dev` с номером.

## Ошибки сборки

GitHub Release может появиться до завершения desktop-задач. Выпуск считается готовым только после успешного завершения всех задач и появления шести ожидаемых файлов.

Задачу, прерванную временной ошибкой runner, можно запустить повторно: она использует тот же коммит. Если ошибка находится в исходниках или workflow, исправление выпускается с новой версией. Изменения другой ветки не меняют уже созданный тег.

## Инфраструктура PyPI

Trusted Publisher в PyPI должен быть связан с проектом `ranobe-downloader`, этим GitHub-репозиторием, workflow `release.yml` и environment `pypi`. Владелец в настройках publisher должен совпадать с владельцем репозитория.

Environment `pypi` ограничивает публикацию тегами `v*`; при необходимости для него включается ручное подтверждение. Публикация использует OpenID Connect, поэтому API-токен PyPI в секретах репозитория не нужен.

Если репозиторий ограничивает сторонние actions, в списке разрешённых должен присутствовать `pypa/gh-action-pypi-publish@release/v1`. Разрешать все сторонние actions для этого не требуется.

Слияние PR и обычный push ветки не запускают PyPI job. Публикация начинается после отправки нового тега и успешной сборки GitHub Release и desktop-файлов. Job использует environment `pypi` и выдаёт `id-token: write` только шагам загрузки артефактов и публикации; исходники в нём не исполняются.

После публикации проверяются страница проекта в PyPI, номер версии и установка в чистое окружение:

```bash
python -m pip install "ranobe-downloader==X.Y.Z"
ranobe --version
```

PyPI не позволяет заменить уже опубликованный файл. Если часть артефактов успела загрузиться, состояние wheel и исходного архива проверяется отдельно; изменённые файлы публикуются только под новой версией. Этот workflow не использует TestPyPI.
